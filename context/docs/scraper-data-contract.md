# Scraper Data Contract

What `lineup-scraper` may write to the Lineup database, and the rules every row must satisfy. **The backend owns this contract**, as it owns the schema. When a backend migration touches a content table, this file is regenerated in `lineup-backend/context/docs/` and pasted over `lineup-scraper/context/docs/data-contract.md`.

## 1. Ground rules

1. **Write through Prisma only**, with the copied `schema.prisma` and `@prisma/adapter-pg`. Never run `prisma migrate`, `prisma db push` or hand-written DDL.
2. **Ids are generated by the Prisma client, not the database.** Every `id` is `UUID NOT NULL` with **no database default**: Prisma's `@default(uuid(7))` fills it. A raw `INSERT` without an id fails.
3. **`updated_at` has no database default either.** Prisma's `@updatedAt` sets it. `created_at` defaults to `CURRENT_TIMESTAMP`.
4. **Rows are keyed by natural keys**, never by uuid: `slug` for competitions, clubs, players and matches. The loader looks rows up by key and keeps the uuid the database already has. `transfermarkt_id` on clubs, players and matches (R1) is a **second** unique key: the loader writes it and checks it never points at two rows, but never looks rows up by it.
5. **Diff, then write.** Update only what differs, so a rerun changes nothing and `updated_at` stays put (backend B09).
6. **Validate before the first write.** Every CHECK below is mirrored in the scraper's dataset schema. The database is the last line of defence, not the first.
7. **Error messages name paths, never values.** A failure must not print a player name, an alias or an XI.

## 2. Content tables the scraper may write

Types are PostgreSQL types. "Null" means the column accepts `NULL`. Every table also has `id UUID` (primary key), `created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP` and `updated_at TIMESTAMP(3) NOT NULL`. They are not repeated below.

### 2.1 `competitions` (Prisma `Competition`)

| Column | Prisma field | Type | Null | Notes |
| --- | --- | --- | --- | --- |
| `slug` | `slug` | `TEXT` | no | Natural key |
| `kind` | `kind` | `competition_kind` | no | `league`, `ucl`, `uel`, `world_cup`, `euro` |
| `name` | `name` | `TEXT` | no | Display name, sent to clients |

- **Unique:** `competitions_slug_key (slug)`
- **CHECK `competitions_text_check`:** `btrim("slug") <> '' AND btrim("name") <> ''`

### 2.2 `seasons` (Prisma `Season`)

| Column | Prisma field | Type | Null | Notes |
| --- | --- | --- | --- | --- |
| `competition_id` | `competitionId` | `UUID` | no | FK → `competitions.id` |
| `label` | `label` | `TEXT` | no | `2004-05` (club season) or `2006` (tournament); sent to clients as `season` |
| `start_year` | `startYear` | `INTEGER` | no | The first four characters of `label`, as a number |

- **Unique:** `seasons_competition_id_label_key (competition_id, label)`
- **FK:** `competition_id` → `competitions.id`, `ON DELETE RESTRICT`
- **CHECKs:**

  ```sql
  -- seasons_label_format_check
  CHECK ("label" ~ '^[0-9]{4}(-[0-9]{2})?$')
  -- seasons_start_year_range_check
  CHECK ("start_year" BETWEEN 2000 AND 2025)
  -- seasons_label_start_year_check
  CHECK (left("label", 4) = "start_year"::text)
  -- seasons_label_consecutive_check: 2004-05, 2009-10, 2099-00
  CHECK (
      length("label") = 4
      OR right("label", 2) = lpad((("start_year" + 1) % 100)::text, 2, '0')
  )
  ```

### 2.6 `player_aliases` (Prisma `PlayerAlias`)

The answer matcher reads only `normalized`.

| Column | Prisma field | Type | Null | Notes |
| --- | --- | --- | --- | --- |
| `player_id` | `playerId` | `UUID` | no | FK → `players.id` |
| `alias` | `alias` | `TEXT` | no | Raw form, as written (`İbrahimović`) |
| `normalized` | `normalized` | `TEXT` | no | **Exactly** `normalizeName(alias)` (§ 5) |

- **Unique:** `player_aliases_player_id_normalized_key (player_id, normalized)`. Two aliases of one player that normalise alike are one alias; keep one.
- **FK:** `player_id` → `players.id`, `ON DELETE CASCADE`
- **CHECKs:**

  ```sql
  -- player_aliases_alias_check
  CHECK (btrim("alias") <> '')
  -- player_aliases_normalized_check (shape only; SQL never re-implements the normaliser)
  CHECK ("normalized" ~ '^[a-z0-9]+( [a-z0-9]+)*$')
  ```

- The same normalised alias may belong to two **different** players (two "Silva"s). That is allowed and expected; backend B29 resolves it inside the XI.

### 2.7 `matches` (Prisma `Match`)

| Column | Prisma field | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- | --- |
| `slug` | `slug` | `TEXT` | no | | Natural key |
| `season_id` | `seasonId` | `UUID` | no | | FK → `seasons.id` |
| `date` | `date` | `DATE` | no | | Write `new Date('YYYY-MM-DDT00:00:00Z')`; read back as UTC midnight |
| `stage` | `stage` | `TEXT` | yes | | English display text: `Final`, `Semi-final`, `Matchday 34` |
| `nickname` | `nickname` | `TEXT` | yes | | `Miracle of Istanbul`; sent to clients |
| `extra_time` | `extraTime` | `BOOLEAN` | no | `false` | |
| `shootout_home` | `shootoutHome` | `INTEGER` | yes | | Penalty shootout score |
| `shootout_away` | `shootoutAway` | `INTEGER` | yes | | |
| `transfermarkt_id` | `transfermarktId` | `TEXT` | yes | | The Transfermarkt match-report id, digits only. Never sent to a client |

- **Unique:** `matches_slug_key (slug)`, `matches_transfermarkt_id_key (transfermarkt_id)`; many rows may be `NULL`. **Index:** `matches_season_id_idx (season_id)`
- **FK:** `season_id` → `seasons.id`, `ON DELETE RESTRICT`
- **CHECKs:**

  ```sql
  -- matches_text_check
  CHECK (
      btrim("slug") <> ''
      AND ("stage" IS NULL OR btrim("stage") <> '')
      AND ("nickname" IS NULL OR btrim("nickname") <> '')
  )
  -- matches_shootout_check: both scores or neither, never a draw
  CHECK (
      ("shootout_home" IS NULL) = ("shootout_away" IS NULL)
      AND (
          "shootout_home" IS NULL
          OR ("shootout_home" >= 0 AND "shootout_away" >= 0
              AND "shootout_home" <> "shootout_away")
      )
  )
  -- matches_transfermarkt_id_check (NULL passes)
  CHECK ("transfermarkt_id" ~ '^[0-9]+$')
  ```

- The match score is not here: it is `match_teams.goals` for each side. It includes extra time; the shootout is separate. Don't assume the two sides' `goals` are equal when a shootout exists, since a two-legged tie can go to penalties on aggregate.

### 2.8 `match_teams` (Prisma `MatchTeam`)

Exactly two rows per match: `home` and `away`.

| Column | Prisma field | Type | Null | Notes |
| --- | --- | --- | --- | --- |
| `match_id` | `matchId` | `UUID` | no | FK → `matches.id` |
| `side` | `side` | `side` | no | `home` or `away` |
| `club_id` | `clubId` | `UUID` | no | FK → `clubs.id` |
| `goals` | `goals` | `INTEGER` | no | Final score for this side |
| `formation` | `formation` | `TEXT` | yes | `4-4-2`. **A match with a `NULL` formation is never played** (§ 9) |

- **Unique:** `match_teams_match_id_side_key (match_id, side)` and `match_teams_match_id_club_id_key (match_id, club_id)`. A club can't face itself.
- **Index:** `match_teams_club_id_idx (club_id)`
- **FKs:** `match_id` → `matches.id`, `ON DELETE CASCADE`; `club_id` → `clubs.id`, `ON DELETE RESTRICT`
- **CHECKs:**

  ```sql
  -- match_teams_goals_check
  CHECK ("goals" >= 0)
  -- match_teams_formation_check: 3-5 lines of 1-9 players, 10 outfield in total
  CHECK (
      "formation" IS NULL
      OR ("formation" ~ '^[1-9](-[1-9]){2,4}$'
          AND formation_outfield_total("formation") = 10)
  )
  ```

  `formation_outfield_total(text)` is a SQL function created by the migration. It sums the dash-separated digits and returns `NULL` for anything malformed.

### 2.9 `lineups` (Prisma `Lineup`)

**The answer key.** Starters only: exactly 11 rows per `match_teams` row. Substitutes are never stored (Hard Constraint 17).

| Column | Prisma field | Type | Null | Notes |
| --- | --- | --- | --- | --- |
| `match_team_id` | `matchTeamId` | `UUID` | no | FK → `match_teams.id` |
| `player_id` | `playerId` | `UUID` | no | FK → `players.id` |
| `slot` | `slot` | `INTEGER` | no | 0–10 (§ 6.6) |
| `position` | `position` | `position_group` | no | `GK`, `DF`, `MF`, `FW`; **fixed by the slot and the formation** (§ 6.6) |

- **Unique:** `lineups_match_team_id_slot_key (match_team_id, slot)` and `lineups_match_team_id_player_id_key (match_team_id, player_id)`
- **Index:** `lineups_player_id_idx (player_id)`
- **FKs:** `match_team_id` → `match_teams.id`, `ON DELETE CASCADE`; `player_id` → `players.id`, `ON DELETE RESTRICT`
- **CHECKs:**

  ```sql
  -- lineups_slot_check
  CHECK ("slot" BETWEEN 0 AND 10)
  -- lineups_goalkeeper_check: slot 0 is the goalkeeper, and no other slot is
  CHECK (("slot" = 0) = ("position" = 'GK'))
  ```

- Not enforced by the database, but required: no player starts for **both** sides of one match (the seed schema checks it).
- **Rewrite a side's XI whole.** Delete that side's 11 rows, then insert 11, inside one transaction. Swapping two players between slots would otherwise break `(match_team_id, player_id)` partway through (backend B09).

  -- match_events_minute_check
  CHECK ("minute" BETWEEN 1 AND 120)

## 4. Delete rules: what can never be deleted

Every foreign key that touches a content table:

| FK | On delete | What it means for the scraper |
| --- | --- | --- |
| `seasons.competition_id` → `competitions` | RESTRICT | A competition with seasons can't be deleted |
| `matches.season_id` → `seasons` | RESTRICT | A season with matches can't be deleted |
| `match_teams.club_id` → `clubs` | RESTRICT | A club that played a match can't be deleted |
| `lineups.player_id` → `players` | RESTRICT | A player in any XI can't be deleted |
| `match_events.player_id` → `players` | RESTRICT | A player in any event can't be deleted |
| `guesses.player_id` → `players` | RESTRICT | **A player someone has guessed can't be deleted**, ever |
| `game_sessions.match_id` → `matches` | RESTRICT | **A match someone has played can't be deleted**, ever |
| `memorability_scores.match_id` → `matches` | RESTRICT | A scored match can't be deleted until its score row is |
| `user_stats.favourite_club_id` → `clubs` | SET NULL | (Not the scraper's concern; it can't delete clubs anyway) |
| `club_aliases.club_id` → `clubs` | CASCADE | |
| `player_aliases.player_id` → `players` | CASCADE | |
| `match_teams.match_id` → `matches` | CASCADE | |
| `lineups.match_team_id` → `match_teams` | CASCADE | |
| `match_events.match_id` → `matches` | CASCADE | |

**The rule:** the scraper **never deletes** a competition, season, club, player or match. It may delete and replace aliases, club aliases, one side's lineup rows, a match's events and a match's score row.

- **To take a match out of the pool**, delete its `memorability_scores` row. In production an unscored match is never selected (§ 9).
- **Rewriting the XI of a match someone has already played** changes what their history refers to. The loader's dry run must flag it.
- **Merging two players** after both are referenced can't be done by deleting one. It needs a backend migration plan. Get entity resolution right before the first load.

## 5. `normalizeName`: the exact rule

`player_aliases.normalized` must be **byte-identical** to the backend's `normalizeName(alias)`. Port this file verbatim to the scraper's TypeScript. Python never normalises.

Source: `lineup-backend/src/game/normalize.ts`

```ts
// Letters NFKD won't decompose; mapped explicitly
const NON_DECOMPOSING: Record<string, string> = {
  ı: 'i',
  ø: 'o',
  ł: 'l',
  đ: 'd',
  ð: 'd',
  æ: 'ae',
  œ: 'oe',
  ß: 'ss',
  þ: 'th',
};

const COMBINING_MARKS = /\p{M}/gu;
// Zero-width space and joiner, soft hyphen, BOM
const FORMAT_CHARACTERS = /\p{Cf}/gu;
const WITHIN_WORD_APOSTROPHES = /['’ʼ`]/g;
const NON_ALPHANUMERIC = /[^a-z0-9]+/g;

export function normalizeName(input: string): string {
  // Marks go before lowercasing: İ loses its dot
  const stripped = input
    .normalize('NFKD')
    .replace(COMBINING_MARKS, '')
    .replace(FORMAT_CHARACTERS, '')
    .toLowerCase();

  const mapped = Array.from(
    stripped,
    (char) => NON_DECOMPOSING[char] ?? char,
  ).join('');

  return mapped
    .replace(WITHIN_WORD_APOSTROPHES, '')
    .replace(NON_ALPHANUMERIC, ' ')
    .trim();
}
```

The steps, in order:

1. Unicode **NFKD** (folds ligatures, fullwidth letters and superscripts too)
2. Strip combining marks (`\p{M}`, all blocks)
3. Strip format characters (`\p{Cf}`: zero-width space and joiner, soft hyphen, BOM)
4. Lowercase. Marks are stripped before this, so `İ` becomes `i` and never `i̇`
5. Map the letters NFKD can't decompose: `ı→i ø→o ł→l đ→d ð→d æ→ae œ→oe ß→ss þ→th`
6. Delete apostrophes inside words: `'`, `’`, `ʼ`, `` ` ``
7. Turn every run of characters outside `[a-z0-9]` into one space, then trim

**Output shape:** `^[a-z0-9]+( [a-z0-9]+)*$`, or the empty string. The function is idempotent.

**An alias that normalises to `''` is invalid** (the seed schema's "Alias must normalize to a name"). That covers every non-Latin name: Cyrillic, Greek and CJK all give `''`. Store a Latin transliteration as the alias instead (`Arshavin` for `Аршавин`).

| `LAST_SEASON_START` | `2025` | Latest season start year (the DB CHECK says the same) |

### 6.2 Competition kinds

`league`, `ucl`, `uel`, `world_cup`, `euro`. Nothing else. A domestic cup, the Club World Cup or the Conference League needs a new enum value. That is a **contract change**: a backend migration, then web, then mobile, before the scraper can load it.

### 6.3 Club kind

`club` or `national_team`. World Cup and Euro matches are played by `national_team` rows. One real-world country is one club row; its slug must not clash with a club's.

### 6.4 Season labels (`seasonIssue`)

The DB CHECKs (§ 2.2) enforce the format, the range and consecutive years. The seed schema adds **date windows**, ported in `seasonIssue` (`lineup-backend/scripts/seed/seed-data.schema.ts`):

```ts
const TOURNAMENT_KINDS = new Set(['world_cup', 'euro']);

export function seasonIssue(label: string, date: string, isTournament: boolean): string | null {
  const start = Number(label.slice(0, 4));
  const end = label.length > 4 ? Number(label.slice(5)) : null;
  if (start < FIRST_SEASON_START || start > LAST_SEASON_START) {
    return 'Season is outside the covered range';
  }
  if (isTournament) {
    if (end !== null) return 'Tournament seasons are a single year';
    return date.startsWith(`${start}-`) ? null : 'Date is outside the season';
  }
  if (end === null) return 'Club seasons span two years';
  if (end !== (start + 1) % 100) return 'Season years must be consecutive';
  const isInSeason = date >= `${start}-07-01` && date <= `${start + 1}-06-30`;
  return isInSeason ? null : 'Date is outside the season';
}
```

| Competition kind | Label | Date must fall |
| --- | --- | --- |
| `world_cup`, `euro` | One year: `2006` | In that calendar year |
| `league`, `ucl`, `uel` | Two years: `2004-05` | 1 July of the first year to 30 June of the second |

Here `TOURNAMENT_KINDS` means **single-year seasons**, and it does not include `ucl`. The pool's `TOURNAMENT_KINDS` (§ 8) is a different list.

> ⚠️ **Real data breaks these date windows. Settle it in S04, and decide each case with the backend.**
>
> - **2019–20 club seasons** finished in July and August 2020 (the UCL final was on 23 August 2020), outside the 30 June window.
> - **Euro 2020** was played in 2021. A label of `2020` with 2021 dates fails the single-year rule.
> - **The 2026 World Cup** would need label `2026`, and **`start_year` 2026 is refused by the database CHECK** (2000–2025). Including it needs a backend migration and a contract change (the season range).
>
> The date windows live only in the seed schema, not the database, so the scraper's port may carry documented exceptions for the first two. The third can't be loaded until the backend changes.

### 6.5 Squad size and formation

- Each side has **exactly 11 starters**, 11 distinct players and 11 distinct slots, 0–10.
- `formation`: digits 1–9 joined by `-`, **3 to 5 lines**, lines summing to **10** (`^[1-9](-[1-9]){2,4}$` plus the total). Valid: `4-4-2`, `4-2-3-1`, `3-5-2`, `4-1-2-1-2`, `5-3-2`. Invalid: `4-4-1` (9), `4-6` (2 lines), `4-1-1-1-1-2` (6 lines), `10-0`.
- Same rule as the contract's `formationSchema` (`lineup-backend/src/contract/match.ts`).

### 6.6 Slot order and positions

**Slot 0 is the goalkeeper.** Slots 1–10 fill the formation's lines **from defence to attack**. Within a line, the web draws slots **right to left** (contract § `RevealedPlayer`); check the web's display requirements doc for the exact layout.

**`position` is not free.** The backend derives it from the formation and refuses an XI whose positions disagree. Source: `lineup-backend/src/game/formation.ts`

```ts
// Slot 0 is the GK; lines fill defence to attack
export function positionForSlot(formation: string, slot: number): PositionGroup | null {
  if (slot === 0) return 'GK';
  if (!Number.isInteger(slot) || slot < 0) return null;
  const lines = formation.split('-').map(Number);
  let lineStart = 1;
  for (const [index, size] of lines.entries()) {
    if (slot < lineStart + size) {
      if (index === 0) return 'DF';
      return index === lines.length - 1 ? 'FW' : 'MF';
    }
    lineStart += size;
  }
  return null;
}
```

The **first line is DF, the last line is FW, every line in between is MF**:

| Formation | Slot 0 | DF | MF | FW |
| --- | --- | --- | --- | --- |
| `4-4-2` | GK | 1–4 | 5–8 | 9–10 |
| `4-2-3-1` | GK | 1–4 | 5–9 (both middle lines) | 10 |
| `3-5-2` | GK | 1–3 | 4–8 | 9–10 |
| `4-1-2-1-2` | GK | 1–4 | 5–8 | 9–10 |
| `4-3-3` | GK | 1–4 | 5–7 | 8–10 |
| `5-3-2` | GK | 1–5 | 6–8 | 9–10 |

So in a `4-2-3-1`, the wingers in the "3" are `MF`, whatever the source calls them. Write `position = positionForSlot(formation, slot)`. Never copy a source's position label.

The database checks only the goalkeeper rule (§ 2.9). **A wrong outfield position passes the database and the selector, then fails when the match is played** (§ 9). The scraper's dataset validation must run `positionForSlot` on every slot.

### 6.7 Matches

- `home` club ≠ `away` club.
- `stage` and `nickname`: `NULL` or non-blank English display text.
- `date`: ISO `YYYY-MM-DD`.

### 6.8 Slugs

- Format: `^[a-z0-9]+(-[a-z0-9]+)*$` (the seed schema's `slugSchema`).
- **Permanent.** The loader keys on them, so a changed slug is a new row, and the old one can't be deleted (§ 4).
- **Reserved prefixes: never start a real slug with these.**

  | Prefix | Used by |
  | --- | --- |
  | `club-`, `nat-` | Mock seed clubs (`club-northgate`, `nat-…`) |
  | `comp-` | Mock seed competitions |
  | `match-` | Mock seed matches |
  | `pl-` | Mock seed players |
  | `test-` | Backend e2e suites, which treat any `test-` row as a leftover |

## 7. `memorability_scores.signals`

A JSON object. **The only part the backend reads is `sides`.** Everything else is the scraper's own per-signal breakdown, for QA (S16) and tuning.

### 7.1 The `sides` block (read by backend B32)

Source: `lineup-backend/src/matches/side-signals.ts`

```ts
const unitSchema = z.number().min(0).max(1);
const strengthSchema = z.object({
  guessability: unitSchema,
  starPower: unitSchema,
});

export const sideSignalsBlockSchema = z.object({
  sides: z.object({ home: strengthSchema, away: strengthSchema }),
});
```

- `sides.home` and `sides.away` both have `guessability` and `starPower`, each a number from **0 to 1**. Other keys alongside `sides` are ignored, since Zod strips them.
- `guessability` comes from the gate (S13); `starPower` from the memorability engine (S10).
- **A missing or invalid block fails silently to neutral (0.5 everywhere)**: no error and no log. A typo here quietly turns every duel into a coin flip, so validate it in the scraper.

**What the backend does with it** (`lineup-backend/src/matches/side-rules.ts`), for duels only:

```text
strength(side) = (guessability + starPower) / 2
P(home)        = clamp(0.5 + (strength(home) - strength(away)) / 2, 0.3, 0.7)
```

The stronger XI is favoured, but each side is chosen at least 30% of the time.

### 7.2 A full example

```json
{
  "stage": 1.0,
  "rivalry": 0.0,
  "drama": 0.92,
  "stakes": 0.85,
  "starPower": 0.8,
  "footprint": 0.97,
  "eraBucket": 0,
  "raw": { "goals": 6, "comebackFromHt": true, "extraTime": true, "shootout": true },
  "sides": {
    "home": { "guessability": 0.9, "starPower": 0.86 },
    "away": { "guessability": 0.82, "starPower": 0.71 }
  }
}
```

Everything except `sides` is illustrative. S10 defines the real keys and records them in its spec.

## 8. `ERA_BUCKETS`, `POOL_THRESHOLD` and the pool's tournament kinds

Source: `lineup-backend/src/matches/pool-rules.ts`

```ts
// By season start year
export const ERA_BUCKETS = [
  { from: 2000, to: 2007 },
  { from: 2008, to: 2015 },
  { from: 2016, to: 2026 },
] as const;

export const TOURNAMENT_KINDS: readonly CompetitionKind[] = ['world_cup', 'euro', 'ucl'];

// Provisional: retuned by B19 and B22
export const POOL_THRESHOLD = { league: 60, tournament: 45 } as const;
```

| Name | Meaning | Who uses it |
| --- | --- | --- |
| `ERA_BUCKETS` | Three eras by **season start year**. Scores are normalised **within** a bucket (spec § A), so the 2000s are not crowded out by better-documented recent matches. The selector also samples across them | Scraper S10 (normalisation), backend selector (sampling) |
| `TOURNAMENT_KINDS` (pool) | Competitions that get the **lower** threshold: `world_cup`, `euro`, **`ucl`**. Everything else, `league` and `uel` included, uses the league threshold | Backend selector |
| `POOL_THRESHOLD.tournament` | **45.** A match in a tournament kind needs `score >= 45` | Backend selector |
| `POOL_THRESHOLD.league` | **60.** Any other match needs `score >= 60` | Backend selector |

- These values are **provisional**. When S10 or S16 wants different numbers, that is a **backend change first** (`pool-rules.ts`). The scraper then copies the new values into its QA config and this contract is regenerated.
- `score` is on the same 0–100 scale in both repos. The scraper's normalisation must produce scores where these thresholds mean what they say: a top memorable final well above 60, a dull league match well below.

## 9. How the backend decides a match is playable

Three layers. A match must pass all three, or it is either never served or fails mid-game.

### 9.1 Selector query (`lineup-backend/src/matches/match-selector.service.ts`, `poolWhere`)

A match is a **candidate** if any of these holds:

1. Its competition kind is in the pool's `TOURNAMENT_KINDS` and it has a `memorability_scores` row with `score >= 45`
2. Its competition kind is not, and it has a `memorability_scores` row with `score >= 60`
3. **Dev only:** it has no `memorability_scores` row at all, and the backend env `MATCH_POOL_INCLUDE_UNSCORED=true`. Production refuses to boot with this flag on, so in production an unscored match is never served.

### 9.2 Completeness (`toCandidate`, standing in for the gate)

The candidate is then dropped unless:

- it has exactly **2** `match_teams` rows,
- both have a non-`NULL` `formation`,
- and both have exactly **11** `lineups` rows.

### 9.3 At play time (`lineup-backend/src/matches/squad-loader.service.ts`)

When the match is picked and a side is chosen, that side's XI is loaded and **throws** (the solo or duel start fails with a server error) if:

- the side has no formation,
- it doesn't have exactly 11 lineup rows,
- any slot's `position` ≠ `positionForSlot(formation, slot)`,
- any starter has **no `player_aliases` row**.

Layers 9.1 and 9.2 don't check positions or aliases, so **a match that breaks 9.3 is served and then fails in front of a player.** The scraper's gate (S13) and dataset validation (S14) must guarantee every 9.3 rule for **both** sides of every scored match. Either side can be picked.

### 9.4 What follows from the pool

- **Stratified sampling** (`sampleStratified`): pick a competition, then an era bucket within it, then a club within that, each weighted by the square root of its size; then one match uniformly.
- **Catalog** (`GET /catalog/filter-options`): the competitions, clubs and era range shown to players are derived from the candidate pool alone. A loaded competition with no candidate match doesn't appear.
- **Empty pool:** if filters match nothing, the backend blames the first filter (competition, then club, then era) whose removal would refill the pool.

## 12. Changing this contract

1. The scraper finds it needs something new: a column, an enum value, a wider season range, a different threshold.
2. That becomes a **backend phase first**: migration and/or constant change, deployed to every Neon branch (`dev`, `ingest`, and `production` once it has a schema).
3. If it reaches what clients see (a new competition kind, the season range, image attribution), it is also a contract change: web, then mobile.
4. The backend regenerates this file.
5. The scraper copies `schema.prisma` and this file, and `npm run db:check` passes.
