## Open Questions

Both settled before `/feature start`.

1. **`@prisma/adapter-neon` or `@prisma/adapter-pg`?** The todo says "the Neon adapter".
   - `PrismaNeon` uses Neon's serverless driver over WebSockets. That suits serverless and edge functions, and needs `ws` on Node.
   - `PrismaPg` uses `pg` over plain TCP. It's the usual fit for a long-running process, and Neon accepts it unchanged.

   **Decided: `@prisma/adapter-pg`.** It's recorded as a deviation from the todo's "Neon adapter" wording. The backend is one persistent NestJS process on Railway or Fly (Hard Constraint 14), not a function, so TCP needs no WebSocket shim. Either way it's still Neon.
2. **Connect at startup, or lazily on the first query?** **Decided: at startup** (`$connect()` in `onModuleInit`). A wrong or unreachable `DATABASE_URL` stops the app before it listens, like B02's env check. The cost is that e2e suites need the network and a real database, which `coding-standards.md` allows ("a disposable Neon branch only").

## Notes

- Scope: Prisma wired into the app and the CLI against the Neon dev branch, with a repeatable migration workflow. No tables yet.
- Depends on: B02 (env schema, `ENV` token) and B03 (envelope filter: a Prisma error must surface as `server_error`, never as SQL).
- **Version trap:** `prisma`'s `latest` npm tag currently points at `8.0.0-rc.19`, while `@prisma/client`'s `latest` is `7.10.0`. A bare `npm install prisma` installs a v8 prerelease against a v7 client. Install both with exact versions.
- Prisma 7 specifics:
  - The connection URL lives in `prisma.config.ts`, not `schema.prisma`.
  - The CLI no longer loads `.env` by itself.
  - The new `prisma-client` generator needs an explicit `output`.
  - Use `moduleFormat = "esm"` and `.js` import extensions so the output works under `nodenext` and the `@/` alias (`@/generated/prisma/client.js`).
- Constraints:
  - Prisma is the only database access, through `PrismaService` (`coding-standards-backend.md` § Data).
  - Migrations only through `prisma migrate`. Never edit an applied migration.
  - Never leak SQL or a Prisma error message to a client. The B03 filter already maps unknown errors to `server_error`.
  - **Never log the squad.** Keep Prisma logging to `warn` and `error`. Never enable `query` logging, which would print lineup rows.
  - `prisma.config.ts` reads `process.env` itself. That's CLI tooling outside the app, so it's the one accepted exception to "only `src/config/` reads `process.env`".
  - `DATABASE_URL` is a secret. The env error output already names the key, never its value.
- Risk to check: `prisma migrate dev` creates a temporary shadow database. On Neon that needs the role to be allowed `CREATE DATABASE`; Neon's default owner role usually is. If not, add a `SHADOW_DATABASE_URL` pointing at a second Neon branch. B04 has no models, so the first real test is B05's migration. Note the outcome there.
- Verification:
  - `npm run db:status` connects to the dev branch and reports no migrations, with no errors.
  - `npm run build`, then `node dist/main.js` connects at startup and listens on 8080.
  - With `DATABASE_URL` removed, the app exits with code 1 and names the key. With an unreachable host, the app exits instead of listening.
  - `npm test`, `npm run test:e2e` (against the dev branch) and `npm run lint` pass.
  - A fresh clone runs `npm ci` and the client is generated without a manual step.

**Deviations recorded during implementation**

- Driver adapter is `@prisma/adapter-pg`, not the Neon adapter in todo.md (Open Questions 1). `pg` comes in as the adapter's own dependency, not a direct one.
- **`$connect()` alone doesn't connect with a driver adapter.** The first run started "successfully" against an unreachable host. `onModuleInit` now also runs `SELECT 1`, and the pool has a 10 s `connectionTimeoutMillis`, so a host that never answers fails in ~11 s instead of hanging.
- `main.ts` catches startup failures and logs one `Startup failed: …` line with exit code 1. Before this, Node printed a line of minified Prisma source. It also calls `enableShutdownHooks()` so SIGTERM closes the pool. Verified that a failed connect prints neither the user nor the password from the URL.
- `prisma.config.ts` reads `process.env.DATABASE_URL` directly rather than Prisma's `env()` helper, which throws when unset. That way `prisma generate` works on a fresh clone with no `.env`.
- `npm run db:status` exits 1 for now. Prisma reports "not managed by Prisma Migrate" until the first migration exists (B05). It does connect.
- Prisma client options: `log: ['warn', 'error']` and `errorFormat: 'minimal'`.
- `src/generated` is also in `.prettierignore`. E2E got `testTimeout` 20 s and `hookTimeout` 30 s for real Neon round-trips.
- **Audit:** `npm audit --omit=dev` reports 4 high-severity issues, all inside the `prisma` CLI (`deepmerge-ts` via `@prisma/config`, and `mysql2`). `@prisma/client` 7 lists `prisma` as a peer, so it's installed even with `--omit=dev`. The running app never loads the CLI, and `mysql2` is never used against Postgres. npm's only fix is a downgrade to Prisma 6. Accepted for now; recheck at B45 before the first deploy.
- `npm ci --omit=dev` was checked: `postinstall` still works, because `prisma` arrives as a peer.
- For B33/B38: Prisma's `error` log prints the arguments of a failed call. A failing squad or guess query could put player data in the server log. Either drop Prisma's own `error` logging in favour of the envelope filter, or check what a failing squad query prints.
- Tests added at `/feature test`: `src/prisma/prisma.service.spec.ts` checks that startup runs a probe query (it fails if the `SELECT 1` is removed), that a failed probe fails startup, and that shutdown disconnects. The e2e test queries `current_database()` on the dev branch.
- Shadow-database risk not yet exercised; B04 has no models. Still to check at B05's first `db:migrate`.
